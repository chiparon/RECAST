# RECAST 项目工作流 LangGraph 无感替换执行计划

日期：2026-11-03
核对基线：`d6b17b319b49d3b27fcf10f8c1ebee69763d3a75`
状态：项目级替换已实现，Windows / WSL 回归和打包已验证；实际范围及验证边界见[实施验证记录](langgraph-transparent-migration-validation.zh-CN.md)。以下保留原执行方案作为对照。

## 1. 目标与范围

把项目级工作流中的执行顺序、条件跳转和循环控制交给 LangGraph，保持用户使用方式和业务行为一致。

本次核心改动是替换 `ProjectPipeline.execute()` 内的手写编排。保留 `ProjectPipeline` 对外入口与既有 Ports，继续调用原来的建模、检索、生成、编译、Verifier、集成和提交能力。

**本次不增加 worker、不改并行度、不增加模型角色，不改变部署方式和验收标准。** 项目模块仍按既有顺序串行执行，任务仍由 VS Code 扩展宿主持有。

Verifier 的 `createAgent` 已基于 LangGraph。本次保持其内部模型—工具循环、外层宿主复核循环及测试纠错复核原样，避免在迁移项目工作流时同时改动验证行为。Verifier 外层循环如以后需要图化，应另做独立的小步替换。

### 无感替换的明确含义

| 用户可观察的部分 | 本次约束 |
| --- | --- |
| 启动 | 继续使用 `npm run dev:extension`；不新增服务、数据库或启动步骤 |
| 操作 | 原有开始、取消、继续、单模块重试、查看输出和导出报告保持不变 |
| 前后端消息 | 保持既有消息类型、字段和业务语义 |
| 进度 | 保持现有阶段、事件顺序、模块信息和错误说明；不把图内部节点名显示给用户 |
| 生成 | 保持提示词、工具、模型配置、参考选择、文件权限及编译命令 |
| 验证 | 保持证据处理、失败分类、反馈与修复上限、验收等级 |
| 恢复 | 升级前的合法运行记录仍能按原规则继续；不要求重新导入或建模 |
| 交付 | 保持独立输出工程、交付测试、报告与本地输出 Git 提交 |

不保证两次真实模型请求生成逐字相同的代码；模型本身具有不确定性。“行为等价”用相同的受控响应严格验证，真实模型运行用于确认接线和完整流程。

## 3. 图的执行节点

主线按下面顺序组织。节点是控制边界，不等于新增业务动作：

```text
START
  ↓
准备新任务 / 恢复原任务
  ↓
选择下一个未完成模块
  ├─ 有模块 → 检索 → 调用现有 generate() → 记录结果 → 回到选择
  └─ 无模块 → 执行既有项目 Integration
                              ↓
                         最终项目验收
                              ↓
                         按原规则分支
                 ┌────────────┼────────────┐
             可集成修复       可交付       禁止交付
                 ↓             ↓             ↓
           集成修复后重验   哈希复核与提交    失败
                               ↓             ↓
                              END           END
```

实施时对应以下节点职责：

| 节点 | 必须复用的现有行为 |
| --- | --- |
| `prepareOrRestore` | 新任务执行准备、保存快照、初始化协议；恢复任务执行原恢复预检和协议恢复，不重新调用协议规划 Agent |
| `selectModule` | 按既有列表顺序选择，不重新计算另一套调度顺序；跳过已完成模块 |
| `retrieve` | 调用原 `ports.search()`，保留候选选择和相关事件 |
| `generateModule` | 整体调用原 `ports.generate()`，包含 Analyzer、Translator、编译、Verifier 和现有修复；不在图外再验一次 |
| `completeModule` | 保留执行能力写入的模块信息、翻译证据和文件范围，保存检查点 |
| `integrate` | 沿用 `proactiveIntegration` 和现有集成任务创建、恢复规则，不重复创建 Integration |
| `validate` | 调用原 `ports.validate()`，记录完整 `validationHistory` |
| `routeValidation` | 按原顺序判定硬性阻断、可修复失败及通过，不把所有失败都交给集成修复 |
| `repairIntegration` | 沿用两次集成修复上限、128 个文件范围上限和诊断传递 |
| `publish` | 计算原验收等级，等待必要保存、核对最终源码哈希，执行原提交能力 |

节点异常、取消和最终清理由现有生命周期外壳统一处理。图不能绕过 `finally`，也不能把到达 LangGraph `END` 等同于业务成功。

## 4. 状态、持久化和恢复

### 4.1 保持一个业务状态更新来源

业务状态继续使用现有 `ProjectPipelineRun`。首版图状态只增加本次执行所需的控制信息，例如模块游标、集成验收尝试计数和路由结果；不再保存第二份可独立修改的业务 `run`。

图节点通过同一个现有业务状态更新路径，修改阶段、当前模块、结果和事件。`current`、消息快照和磁盘记录均从该业务状态生成。控制变量的作用域与原循环一致，不能因为进入或重入节点就重置预算。

特别处理现有 `generate()` 的旁路更新：它除返回翻译结果，还会修改模块的候选选择、`authorizedFiles`、`moduleVerification`、`retainedTests` 等字段。图节点必须保留这些修改，不能只接收返回值而丢失模块证据。

图状态中不放密钥、AbortController、模型客户端、子进程或打开的运行时对象。这些仍由原宿主和执行能力持有。

### 4.2 本次继续使用原持久化

- `run.json` 是唯一持久化业务记录，报告继续从同一记录生成。
- 保持原目录、字段、临时文件加重命名的保存方式，以及保存失败时的处理。
- 不增加 SQLite、Postgres 或独立图检查点数据库，也不把 `run.json` 改成异步投影。
- 项目图首版不依赖 Checkpointer；进程内图状态不承担跨进程恢复职责。
- 现有 Verifier 的 MemorySaver 保持原样，它不提供宿主重启后的会话恢复。

### 4.3 继续按原规则恢复

```text
读取原 run.json
    ↓
原 running 记录转 interrupted
    ↓
原 resume() 计算重试集合并传播下游失效
    ↓
保留原 previous；使用整理后的记录启动一次新的图执行
    ↓
prepareOrRestore 使用未清理的 previous 执行原恢复预检
检查路径、基线、文件范围和哈希
    ↓
保留无关已完成模块，最终项目重新验收
```

这不是 `invoke(null)` 恢复原 Agent 会话。仍然只支持原有恢复粒度，不增加自动续跑、工具调用级恢复或关闭 VS Code 后继续执行。

预检必须使用未清理的原 `previous`，保留当时的进行中模块和授权范围，不能用已经重置状态的记录代替。保持以下边界：恢复预检失败不能刷新可信检查点；发布失败后恢复必须重新最终验收；旧记录没有新图字段也必须能够进入原恢复路径。

## 5. 必须保留的业务不变量

1. **串行与单任务约束**：同一宿主只运行一个项目任务；取消后的清理结束前仍为 busy；完成模块按原规则跳过。
2. **模型输入与调用次数**：不增加模型决策节点，不更改提示词、请求参数、历史参考选择或模型重排，不因图接线重复调用 Verifier。
3. **预算**：Codex Runtime 保持 2 小时配置及原预算作用域；模块生成后最多五轮 Verifier，生产缺陷交回原 Translator，环境问题不据此修改实现。保留现有四次验证修复配置和所有其它预算。
4. **不叠加框架重试**：图节点不配置通用自动重试。保留既有业务位置上的重试，避免一次失败触发两层重跑或重复提交。
5. **验收等级**：未确定或环境问题仍可能得到 `completed + compilation-only`；不得擅自变为必须全部行为通过，也不得冒充 `behavior-verified`。
6. **硬性阻断**：保护文件变化、交付测试失败立即阻止发布；最终生产缺陷阻止交付；完整项目编译和固定测试失败沿用原有限集成修复规则。
7. **最终快照**：行为结论继续绑定最终源码哈希，提交前重新核对；不复用集成前的绿色结论。
8. **失败证据**：测试修订、未解决失败、历史尝试、固定历史版本和交付测试必须保留，不能因恢复或迁移丢失。
9. **保存与通知**：保持现有保存串行化和 UI 即时通知语义，不顺手改成“等待写盘后才通知”。模型进度回调期间也要持续展示信息。
10. **取消和收尾**：先停止并清理子运行，再保存允许范围内的部分写入快照和最终报告；记录持久化失败时仍终止且报告不可用。
11. **图步数限制**：根据节点数、模块数和有限修复次数设置足够的 `recursionLimit`，避免框架默认步数限制提前终止合法大项目；不修改模型和工具预算来规避该问题。
12. **状态名称**：继续保留七个 stage、五个项目 status 和原模块 status；内部图路由不是新的前端状态。

## 6. 分阶段执行与提交

每一步只在本步验收通过后进入下一步。以下是预期实施提交，不表示已经完成。

| 阶段 / 提交 | 工作 | 完成条件 |
| --- | --- | --- |
| P0：固定等价基线 | 保存当前编排的测试基线；建立受控 Ports 响应、事件轨迹和旧运行记录样本；记录当前构建及包体情况 | 原有相关测试通过，样本覆盖成功、失败、取消、恢复和验收等级 |
| P1：实现项目图 | 添加显式 LangGraph 依赖和具体项目图；原执行器仅作为测试基线，生产入口暂不切换 | 新图能以测试替身执行完整成功路径和集成修复路径；主线节点不新增模型调用 |
| P2：接入生命周期 | 保持原 public API，接入取消、进度回调、保存队列、清理和旧记录恢复；验证模块旁路更新 | 启停、取消、保存失败、单模块重试、下游失效和历史证据用例通过 |
| P3：等价对照及集成 | 同一脚本化输入分别运行旧编排和图编排；补齐故障注入、步数限制和打包集成验证 | 无未解释的业务差异；真实文件、编译、测试、Git 输出及恢复行为一致 |
| P4：Windows / WSL 与真实运行 | 分平台安装、构建、测试、打包；分别验证原 UI 操作；在隔离输出中运行一项代表性真实模型任务 | 两个平台入口及交付流程可用；真实模型调用、测试重放及报告有可追溯证据 |
| P5：切换与收敛 | 将生产入口切至图；移除临时双实现选择和旧生产编排，保留等价基线样本及回退说明 | 无需用户新增配置；旧运行记录能恢复；产品不永久维护两套执行器 |

开发期新旧执行器通过测试注入选择，不新增用户设置，不对真实工程双跑。不得以“图路径失败后自动运行旧路径”作为兼容方案。

## 7. 验收方法

### 7.1 确定性等价对照

对旧、新编排注入相同的受控响应，并使用各自独立的输出目录。至少比较：

- 业务 Ports 调用顺序、参数、次数，以及生成、编译、验证和修复次数。
- stage、status、当前模块、事件顺序、业务消息及前端消息载荷。
- 模块候选、授权写入范围、验证证据、重试历史和失效传播范围。
- 最终验收等级、失败原因、报告内容及生产和测试文件内容。
- 取消、子操作结束、资源清理、最终快照和最终保存的先后顺序。

只归一化时间、随机 ID、临时根路径及由这些值产生的元数据；不能忽略失败事实、验收差异、调用次数或文件内容差异。真实模型不参与严格逐字对照。

### 7.2 必测场景

| 场景 | 预期 |
| --- | --- |
| 正常多模块项目 | 原顺序串行执行、集成、最终验收和提交，结果及业务轨迹等价 |
| 无参考仓库 | 沿用按需求直接实现，不新增失败或隐式选择 |
| 中间模块失败 | 停止后续执行，保存失败原因和已完成结果 |
| 单模块重试 | 重置失败模块及受影响下游，保留无关已完成分支 |
| Integration 失败恢复 | 仅重跑必要集成任务，不重复创建或重做已完成模块 |
| 发布失败恢复 | 重新最终验收，再提交 |
| 行为未确定 / 验证环境问题 | 保持原 `compilation-only` 行为和具体原因 |
| 最终生产缺陷 | 禁止交付，不伪装成功 |
| 保护文件变化 / 交付测试失败 | 立即禁止提交，不误入自动修复分支 |
| 编译或固定测试失败 | 保留原集成修复次数及完整尝试历史 |
| 验收后源码变化 | 哈希检查阻止提交 |
| 取消 / 宿主重启 | 取消传递及清理顺序保持；重启记为 interrupted，按原入口恢复 |
| 保存失败 / 恢复预检失败 | 按原规则失败；不洗白外部修改、不丢失旧检查点 |
| 大模块数 / 多次合法回路 | 不被图默认步数限制提前终止，不增加模型调用 |
| 生成期间的回调更新 | 进度持续展示；候选、权限、测试和模块验证结果不丢失 |
| 旧版本记录 | 不增加必填字段，保留旧 checkpoint 缺省时的原兼容路径 |
| 回退读取新记录 | 新引擎生成的失败、取消、中断记录，由基线旧执行器读取并恢复；包含部分生产写入、交付测试和 Integration |

故障注入需覆盖准备、初始化、检索、生成、最终验收、哈希、提交、保存和清理入口。

### 7.3 复用现有测试，而非重写一套“图形通过测试”

优先复用 `project-pipeline.test.ts`、`project-pipeline.integration.test.ts`、`project-pipeline-backend.test.ts`、后端打包集成测试、交付测试集成用例及 Webview 项目流水线测试。

新测试主要证明迁移新增风险：状态更新丢失、框架自动重试、步数提前耗尽、旧记录兼容和新旧轨迹差异。不要只断言图包含哪些节点。

真实模型任务单独记录使用的平台、模型、输入、输出、编译结果、Verifier 结果、交付测试重放及恢复结果。已有可用授权配置才用于实施验证，文档和日志不保存密钥。未完成真实验证时明确标为未验，不把测试替身结果当成真实业务验收。

### 7.4 Windows 与 WSL 验证顺序

实施时先在当前平台执行 `npm run workspace:check`，再使用工具链。确认两边 Git HEAD 一致后，通过 `npm run workspace:sync -- --to wsl` 同步当前源代码；依赖清单变化时，在 WSL 自己的目录执行 `npm ci`。冲突按源代码解决，不强制覆盖或删除同步基线。

两个平台分别执行以下适用检查，不能共享 `node_modules`、`dist` 或运行时缓存：

```text
npm run workspace:check
npm run typecheck --workspace forexplore-vscode
npm run build:extension
npm run test --workspace forexplore-vscode -- --maxWorkers 2
npm run test:verifier
npm run test:scripts
npm test
npm run package:extension
```

先跑相关用例和等价对照，通过后再做切换前全量回归。实际源码集成测试之外，还需核验构建后的扩展和 VSIX 能加载 LangGraph。平台自身不支持的用例应注明跳过原因，由另一平台或对应验证补齐，不能笼统写“两端全部通过”。

## 8. 回退方式

1. 发布前保留基线代码和可用扩展包；本次不改运行记录格式，也不新增必须迁移的数据。用新引擎实际生成的失败、取消和中断记录反向验证旧执行器恢复，不能只凭 JSON 格式相同认定可回退。
2. 发现差异时停止新引擎切换，修复该差异；不在已经修改文件的任务中自动换旧引擎重跑。
3. 已切换版本需要回退时，先取消运行并等待清理，切回原扩展包，再通过原任务继续入口恢复。
4. 不删除输出工程、检查点、测试证据或历史报告来“修复兼容”。硬崩溃仍按原中断恢复规则处理。

## 9. 最终交付清单

- [ ] 项目级编排由 LangGraph 管理，原 public API 和业务能力保持一致。
- [ ] 新旧受控执行的业务轨迹、结果与副作用对照通过，无未解释差异。
- [ ] 开始、取消、继续、单模块重试、导出与进度显示保持原有交互。
- [ ] 原有状态、消息、验收等级、提示词、工具和预算均保持。
- [ ] 升级前记录可恢复，新记录经旧执行器恢复也通过；失败证据、部分写入保护与交付测试不丢失。
- [ ] 无新增服务、数据库、密钥配置、启动命令或并行 worker。
- [ ] Windows 与 WSL 的类型检查、构建、相关及全量回归、打包按平台完成。
- [ ] 真实任务运行和交付测试重放完成，并明确记录实际验证范围。
- [ ] 移除临时双实现，保留可重复运行的等价基线和回退说明。

验收重点是业务行为等价，而不是框架接入或图能够运行。预计直接收益是项目级执行路径可显式检查和可视化；本次不把速度提升、并行执行或更细断点恢复列为承诺。
