# 项目级需求流水线实现与验证

项目执行链路位于 `apps/vscode-extension/src/project-pipeline*.ts`，项目与单模块界面分别位于 `webview/src/components/ProjectPipelineWorkbench.tsx` 和 `PipelineWorkbench.tsx`。

## 已接入的执行链路

默认入口为整个已选目标项目：需求文档 → 固定结构索引、项目建模与源文件快照 → 模块依赖排序 / 循环依赖合并 → 逐模块检索 → Analyzer 计划 → Translator 生成与编译修复 → 完整项目编译和固定行为测试 → 必要时集成修复并再次验证 → 输出副本中的原子 Git 提交 → Markdown / JSON 验收报告。

半自动模式在建模结果、候选与范围、修改计划、最终验收四类节点等待确认。候选和计划节点按模块重复；审阅意见进入生成上下文，计划意见在 Translator 写入前生效。每次决定与当前证据哈希绑定，取消、退回或宿主重启使未消费的审批失效。

所有生成在扩展管理的独立副本中执行。验收测试、构建配置及范围外文件的改动会阻止发布。验证到批准期间产物变化会阻止提交。失败和取消保留执行副本及报告；重启后明确标为中断，并要求重新执行和验证。

## 自动化验证

- 扩展完整测试：55 个测试文件、314 项测试通过。
- 本次直接涉及的运行时与 HTTP 接口：34 项测试通过，包含新增的计划审阅前禁止写入和审阅意见传递测试。
- 实际集成测试执行了隔离复制、代码写入、Node 语法检查、固定验收脚本、真实 Git 提交、报告持久化和重启恢复。模型响应在该测试中由可重复的工具调用脚本提供；没有把此结果当作真实模型或 Java / C# 项目的成功率。
- 类型检查、后端 TypeScript 构建、扩展构建通过。
- 前端验证覆盖无需选模块即可启动项目、四类确认令牌、取消、差异查看、报告导出、日志上翻和状态恢复。

## 界面层级与响应式验证

项目工作台初始只显示「01 准备任务」，工程资源默认收起。需求区支持拖拽或点击导入单个 UTF-8 TXT / Markdown 文件，沿用 8000 字限制；不支持、空白、超长或多文件导入保留原文，运行中禁止替换需求。启动栏保持可见；点击开始后收起输入配置，展示统一的「02 任务执行」区域，集中放置目标项目、当前模块、完成数量、阶段进度、人工审阅、失败处理、交付结果、实时日志和模块明细。

浏览器使用明确标注的示例数据检查了初始准备、点击开始和集中执行的界面，覆盖 1366×900 和 430×900。开始前没有进度或日志占位，开始后两者均位于同一个执行区域，未发现横向溢出。拖拽导入与文件校验测试、类型检查和生产构建通过，扩展安装包随界面更新。

单模块调试同步使用相同的准备与集中执行布局、拖拽导入和按需展开的配置。运行时不再重复展示独立进度动画，生成范围折叠展示，取消、状态恢复、候选确认、生成前确认、文件差异和回滚入口保留。重新切入单模块调试后仅显示准备任务，不会因旧作用域自动生成。同步后扩展完整回归 314 项通过；新增单模块拖拽、页面状态和视图切换检查，并复用原有自动 / 半自动、日志跟随、轮询失败恢复和回滚测试。

## 环境与验证限制

本机未发现 Java / Maven 工具链；`dotnet --list-sdks` 没有列出 SDK。真实 Java / C# 工程执行需先具备相应 SDK、模型凭据和用户级编译 / 验收设置，本次没有运行真实模型生成的 Java / C# 全项目验收。

尝试后端全量回归时，Windows 环境有既有测试不能通过：Codex 测试直接执行带 POSIX shebang 的 `.mjs` 假程序，另有 .NET 模块准备测试依赖未安装的 SDK。配置捆绑 Python、关闭测试进程的 Git 换行转换并提高 Git 密集测试超时后，排除该 POSIX 假程序测试文件的运行结果为 234 项通过、1 项跳过、1 项因 .NET SDK 不可用而失败。相关运行时和 HTTP 的独立测试均通过；没有将后端全量回归记录为全部成功。

覆盖率未采集时，报告明确显示“未采集”。未配置固定行为测试时，仅记录编译通过，不声称业务行为已经验收。
