# 生成测试随项目交付

全自动项目流水线会把模块 Verifier 生成的测试、测试数据和必要运行配置保留到输出项目。原始目标骨架仍由独立输出副本保护。

## 用户操作

1. 正常导入目标项目、填写需求并点击「开始执行」。
2. 在模块明细的「保留测试」中展开查看文件；运行中断或失败时，已写入的测试仍可在执行副本中查看。
3. 完成后打开输出项目。生产代码、生成测试、测试配置和说明在同一个输出 Git 提交中。
4. 安装项目正常需要的构建与测试依赖后，在输出项目根目录执行：

   ```sh
   node .recast-tests/run.cjs
   ```

该入口会依次运行所有保留的模块测试。单模块命令记录在对应 `manifest.json` 的 `command` 字段中。

## 目录与依赖

每个模块按稳定标识得到一个固定目录 `.recast-tests/<模块标识的摘要>/`，包含：

- `manifest.json`：框架、测试路径、文件 SHA-256、生成阶段最后状态和执行命令。
- `run.cjs`：可移动的模块测试入口。
- 必要的测试项目配置，例如 xUnit 测试工程、Maven POM、CMake 测试工程。
- `tests/`：独立测试工程的测试源码及数据。

已有测试根目录可用时，生成源码放在该目录下的 `recast/<模块摘要>/`，以复用现有项目的测试依赖与配置。已有企业测试不能被生成测试覆盖。C# 独立测试项目放在点号目录中，避免被生产项目的默认源码通配符误编译。

执行入口需要 Node.js 20+，以及对应语言的正常工具链和测试依赖：pytest、Jest/Vitest、JDK 与 Maven/Gradle、.NET SDK，或 CMake 3.21+、GCC/G++ 与匹配版本的 gcov。Node 测试使用目标项目安装的框架；Python 优先使用目标项目的 `.venv`，也可通过 `PYTHON_COMMAND` 指定解释器。原生工具可通过 `CMAKE_COMMAND`、`GCOV_COMMAND` 指定。项目需要的依赖仍需正常安装，不把本机依赖目录随项目复制。

Python 模块会额外交付 `requirements.txt`，可在目标项目的虚拟环境中通过 `python -m pip install -r .recast-tests/<模块摘要>/requirements.txt` 安装测试依赖。

生产项目引用采用相对路径。Maven 独立测试会先重新构建生产项目；C/C++ 测试重新构建实际库目标，读取项目 `.recast-native.json` 的库选择与配置。构建产物、覆盖率报告和运行缓存不进入交付提交。

## 验收与恢复

- 每次写测试和执行测试后保存测试清单。临时验证副本结束清理时，输出项目仍保留这些文件。
- 文件先完整暂存，再应用到输出目录；应用中发生进程中断时，断点恢复会核对摘要并完成未结束的交付。
- 模块重试沿用原目录，不为每轮创建新的交付副本；原有执行失败与纠错证据继续保留。
- 最终整合后在**输出项目的交付位置**重新执行保留测试；如配置了固定企业验收，也会针对更新后的最终项目再次执行。
- 测试重放失败会阻止发布，并在报告中给出实际输出。可以重试失败模块，也可以保留代码与测试继续排查。
- 验收和提交共同绑定生产代码、测试源码与配置的内容摘要；验收后改动任何交付测试都会阻止发布。

测试重放成功不等于所有需求已经获得证明。最终行为结论仍取决于 Verifier 的覆盖、历史失败是否已正确解决，以及已有固定验收结果；本次改动不放宽这些规则。

如果曾经失败的测试被修改，Verifier 会检查纠错是否保留需求断言。文件版本会去重，并按模型上下文预算分批检查，不再设置固定字符总量上限。每批都保留完整需求、当前测试与相关生产代码，全部通过才解除历史失败；不会截掉断言来换取通过。普通绿测、编译修复以及未改测试就已修复的生产缺陷不额外触发这项检查。

兼容模型接口未提供上下文容量时，可在启动 RECAST 前设置 `TRANSLATION_VERIFIER_REVIEW_CONTEXT_TOKENS` 为模型实际支持的上下文 token 数。服务端仍判定输入超限时会进一步拆批；单个测试及其关联上下文本身仍超限时，工作台会保留未确认原因，需拆分过大的测试/数据文件或使用更大上下文模型。
